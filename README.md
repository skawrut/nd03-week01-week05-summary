## ภาพรวมการเรียนรู้

ตลอดห้าสัปดาห์ ผู้เรียนได้เปลี่ยนกรอบความคิดจากระบบควบคุมที่มีศูนย์กลางและทำงานตามรอบสแกน ไปสู่ระบบที่ประกอบด้วยโปรแกรมย่อยหลายส่วนหรือ **Node** ซึ่งทำงานอย่างอิสระและแลกเปลี่ยนข้อมูลผ่าน **Topic** แนวทางนี้ช่วยให้ระบบแบ่งหน้าที่ชัดเจน ขยายได้ง่าย และรองรับอุปกรณ์ตั้งแต่ไมโครคอนโทรลเลอร์ เครื่องคอมพิวเตอร์ ไปจนถึงระบบวิเคราะห์ข้อมูลและ Digital Twin

ลำดับการเรียนรู้โดยรวมสามารถสรุปได้ดังนี้

```text
พื้นฐาน Automation
        ↓
Node และ Topic แบบ Event-driven
        ↓
Message / Service / Action / Parameter / TF
        ↓
การสังเกต บันทึก และเล่นข้อมูลย้อนหลัง
        ↓
Digital Twin และการเชื่อมต่ออุปกรณ์จริง
```

## Week 01 — Introduction

สัปดาห์แรกเป็นการแนะนำขอบเขตของสาย Automation, Robotics และ Machinery Industry พร้อมวางบริบทว่าระบบอัตโนมัติสมัยใหม่ไม่ได้มีเพียง PLC, DCS หรือ SCADA แต่กำลังเชื่อมโยงกับหุ่นยนต์ ระบบกระจาย Edge Computing และ AI มากขึ้น

ประเด็นสำคัญคือความรู้เดิมด้าน sensor, actuator, control loop, safety และ process engineering ยังคงเป็นพื้นฐานที่จำเป็น สิ่งที่เปลี่ยนแปลงคือสถาปัตยกรรมซอฟต์แวร์ส่วนกลาง จากโปรแกรมขนาดใหญ่ที่ควบคุมทุกอย่าง ไปเป็นส่วนประกอบขนาดเล็กที่สื่อสารกันผ่านเครือข่าย

สิ่งที่ได้รับจากสัปดาห์นี้ ได้แก่

- เห็นภาพรวมและทิศทางของระบบ Automation และ Robotics สมัยใหม่
- เข้าใจบทบาทของ Middleware ในการเชื่อมอุปกรณ์และซอฟต์แวร์หลายส่วน
- รู้จักแนวคิด Digital Twin ในฐานะแบบจำลองดิจิทัลที่เชื่อมโยงกับเครื่องจริง
- เตรียมกรอบความคิดสำหรับการเรียนรู้ ROS-style architecture ในสัปดาห์ต่อไป

## Week 02 — ROS-style Middleware และ Digital Twin

Week 02 เน้นการสร้างความเข้าใจเชิงแนวคิด โดยเปรียบเทียบระบบเดิมแบบ PLC/DCS กับระบบกระจายแบบ ROS และ `robotos`

### 1. จาก Scan Cycle สู่ Event-driven Architecture

ระบบ PLC แบบดั้งเดิมมักทำงานตามลำดับ อ่านอินพุต ประมวลผล และเขียนเอาต์พุตซ้ำเป็นรอบ ขณะที่ระบบ ROS-style แบ่งงานออกเป็น Node หลายตัว แต่ละ Node มีจังหวะการทำงานของตนเองและตอบสนองเมื่อมีข้อมูลหรือเหตุการณ์เกิดขึ้น

ข้อดีของแนวทางนี้คือสามารถแยกส่วนของระบบ เพิ่มหรือลดองค์ประกอบ และกระจายการทำงานไปยังหลายอุปกรณ์ได้โดยไม่ต้องแก้ไขโปรแกรมศูนย์กลางทั้งหมด

### 2. Node, Topic และ Graph

- **Node** คือโปรแกรมหรือองค์ประกอบที่รับผิดชอบงานเฉพาะอย่าง เช่น อ่านเซนเซอร์ ควบคุมมอเตอร์ แสดงผล หรือวิเคราะห์ข้อมูล
- **Topic** คือช่องทางข้อมูลที่มีชื่อ Node ผู้ผลิตส่งข้อมูลด้วยการ Publish และ Node ที่สนใจรับข้อมูลด้วยการ Subscribe
- **Graph** คือภาพรวมความสัมพันธ์ของ Node และ Topic ทั้งหมดในระบบ

Publisher และ Subscriber ไม่จำเป็นต้องรู้จักกันโดยตรง จึงช่วยลดการผูกติดระหว่างองค์ประกอบ ข้อมูลจาก Publisher หนึ่งตัวสามารถส่งต่อให้หน้าจอ ระบบแจ้งเตือน ตัวบันทึกข้อมูล และ Digital Twin ได้พร้อมกัน

### 3. Message และ Schema

Message คือข้อมูลที่ส่งผ่านระบบ ส่วน Schema เป็นข้อตกลงเกี่ยวกับโครงสร้าง ชนิดข้อมูล หน่วย และความหมายของ Message

การกำหนด Schema ที่ชัดเจนช่วยให้โปรแกรมซึ่งพัฒนาด้วยภาษาต่างกันสามารถทำงานร่วมกัน ลดความผิดพลาดจากการตีความข้อมูล และรองรับการเปลี่ยนแปลงของระบบในอนาคตได้ดีกว่าการส่งข้อมูลดิบหรือใช้ tag ที่ไม่มีโครงสร้าง

### 4. รูปแบบการสื่อสาร

ระบบเลือกใช้รูปแบบการสื่อสารตามลักษณะของงาน

| รูปแบบ | ลักษณะ | ตัวอย่างการใช้งาน |
|---|---|---|
| **Topic** | กระแสข้อมูลต่อเนื่องแบบ Publish/Subscribe และไม่ต้องมีคำตอบ | ค่าเซนเซอร์ สถานะเครื่อง Telemetry |
| **Service** | Request/Response สำหรับงานสั้นที่ให้ผลลัพธ์ทันที | อ่านสถานะ รีเซ็ตตัวนับ เปลี่ยนโหมด |
| **Action** | งานระยะยาว มี Goal, Feedback, Result และยกเลิกได้ | เคลื่อนแขนกล รันรอบการผลิต นำทางหุ่นยนต์ |

หลักการสำคัญคือ งานที่ใช้เวลานานหรือจำเป็นต้องติดตามความคืบหน้าไม่ควรใช้ Service แต่ควรใช้ Action เพื่อให้ผู้ใช้รับ Feedback และยกเลิกงานได้อย่างปลอดภัย

### 5. Parameter และ Lifecycle

Parameter คือค่าตั้งที่ Node เป็นเจ้าของ เช่น อัตราการส่งข้อมูล ค่า Threshold โหมดทำงาน หรือความเร็วสูงสุด ผู้ใช้สามารถเปลี่ยนค่าได้ระหว่างที่ระบบทำงานโดยไม่ต้องแก้ไขหรือคอมไพล์โปรแกรมใหม่

Lifecycle อธิบายสถานะการทำงานของ Node เช่น ยังไม่ได้ตั้งค่า พร้อมทำงาน กำลังทำงาน หรือหยุดทำงาน ช่วยให้การเริ่มและหยุดระบบที่มีหลายองค์ประกอบเป็นไปอย่างมีลำดับและตรวจสอบได้

### 6. TF และระบบพิกัด

ในระบบหุ่นยนต์ ข้อมูลตำแหน่งจะมีความหมายก็ต่อเมื่อระบุกรอบอ้างอิงหรือ **Frame** เช่น `world`, `map`, `base`, `camera` หรือ `tool`

TF หรือ Transform ใช้อธิบายความสัมพันธ์ด้านตำแหน่งและการหมุนระหว่าง Frame ต่าง ๆ เมื่อเชื่อมความสัมพันธ์เหล่านี้เป็น Frame Tree ระบบจะสามารถแปลงข้อมูลจากพิกัดของเซนเซอร์ไปยังพิกัดของหุ่นยนต์หรือโลกจริงได้อย่างถูกต้อง ซึ่งเป็นพื้นฐานของการนำทาง การมองเห็นด้วยกล้อง และการแสดงผลใน Digital Twin

### 7. การสังเกตและแก้ปัญหาระบบกระจาย

เนื่องจากระบบไม่มีโปรแกรมเดียวที่เห็นทุกอย่าง การตรวจสอบจึงอาศัยเครื่องมือหลายรูปแบบ ได้แก่

- Inspect Graph เพื่อดู Node, Topic และความสัมพันธ์ในระบบ
- Watch หรือ Echo Message เพื่อดูข้อมูลที่กำลังไหล
- Record เพื่อบันทึก Message พร้อมเวลา
- Replay เพื่อนำข้อมูลเดิมกลับมาทดสอบซ้ำ

แนวทาง Record/Replay มีบทบาทคล้าย Historian ในโรงงาน และช่วยจำลองเหตุขัดข้องที่เกิดขึ้นแล้วโดยไม่ต้องรอให้ปัญหาเกิดซ้ำกับเครื่องจริง

### 8. QoS และ Determinism

ระบบ Publish/Subscribe ต้องเลือกคุณภาพการส่งข้อมูลให้เหมาะกับงาน เช่น ต้องการข้อมูลล่าสุด ต้องการรับครบทุกข้อความ หรือยอมให้ข้อมูลบางส่วนสูญหายเพื่อแลกกับความหน่วงต่ำ อย่างไรก็ตาม งานควบคุมที่ต้องการเวลาตอบสนองแน่นอนควรแยก Hard Real-time Control ไว้ใกล้อุปกรณ์ และใช้ Middleware สำหรับการประสานงาน การติดตาม และการส่งข้อมูลระดับระบบ

### 9. Digital Twin ร่วมกับ Middleware

Digital Twin ไม่ใช่เพียงภาพสามมิติหรือ Simulation ทั่วไป แต่เป็นตัวแทนดิจิทัลของเครื่องจริงที่ได้รับข้อมูลสดอย่างต่อเนื่อง Middleware ทำหน้าที่เป็นเส้นทางข้อมูลจากเครื่องจริงเข้าสู่ Twin และอาจส่งคำสั่งจาก Twin กลับไปยังเครื่องจริงหลังผ่านการตรวจสอบ

การประยุกต์ใช้ที่สำคัญ ได้แก่

- Shadow Monitoring เพื่อติดตามสถานะและตำแหน่งจริง
- Virtual Commissioning เพื่อทดสอบ Logic ก่อนติดตั้งบนเครื่องจริง
- Safe Command Preview เพื่อจำลองผลของคำสั่งก่อนอนุมัติให้ทำงาน
- What-if Analysis และการฝึกอบรมโดยไม่เสี่ยงต่ออุปกรณ์จริง

## Week 03 — Hands-on with `robotos`

Week 03 เปลี่ยนจากการเรียนแนวคิดไปสู่การลงมือปฏิบัติบนคอมพิวเตอร์ โดยยังไม่ต้องใช้อุปกรณ์จริง ผู้เรียนใช้ `robotos` CLI, Python SDK และ Inspector เพื่อสร้างและสังเกต Graph

### Workshop 01: ติดตั้งและสำรวจ Graph

- ติดตั้งและตรวจสอบ `robotos` ตามระบบปฏิบัติการ
- ใช้ CLI ตรวจสอบเวอร์ชันและคำสั่งพื้นฐาน
- เปิด Inspector ที่ทำงานในเครื่อง
- สังเกต Node ตัวอย่างปรากฏและหายไปจาก Graph

### Workshop 02: Publish และ Subscribe

- สร้าง Publisher จำลองค่าเซนเซอร์
- สร้าง Subscriber เพื่อรับและประมวลผลข้อมูล
- ใช้ CLI และ Inspector ดู Message ที่ไหลผ่าน Topic
- ทดลองหลักการ Decoupling โดยให้หลาย Consumer รับข้อมูลชุดเดียวกัน

### Workshop 03: Service

- สร้าง Service Server สำหรับรับ Request และส่ง Response
- สร้าง Client เพื่อเรียกใช้ Service
- ตรวจสอบ Service ผ่าน CLI
- เปรียบเทียบ Service กับ Topic และเลือกใช้ให้เหมาะกับงานสั้นแบบถาม–ตอบ

### Workshop 04: Action

- สร้าง Action Server และ Action Client
- ส่ง Goal และติดตาม Feedback ระหว่างทำงาน
- รับ Result เมื่อการทำงานสิ้นสุด
- ทดลองยกเลิก Goal ที่กำลังทำงาน

### Workshop 05: Parameter

- ประกาศ Parameter ภายใน Node
- อ่านและเปลี่ยนค่าผ่าน CLI ขณะ Node ทำงาน
- สังเกตผลของการปรับค่าแบบ Live Reconfiguration
- ทำความเข้าใจความแตกต่างระหว่าง Parameter ซึ่งเป็นค่าตั้ง กับ Topic ซึ่งเป็นกระแสข้อมูล

### Workshop 06: Record และ Replay

- สร้างข้อมูลบน Topic แล้วบันทึกลงไฟล์ `.rbag`
- ตรวจสอบระยะเวลา จำนวน Message และรายละเอียด Topic ในไฟล์
- เล่นข้อมูลย้อนหลังเข้าสู่ Graph
- ใช้ข้อมูลเดิมทดสอบ Subscriber หรือระบบวิเคราะห์โดยไม่ต้องเปิด Publisher จริง

### Workshop 07: Mini Digital Twin

- สร้างโปรแกรมจำลองเครื่องจักรที่ Publish สถานะ
- สร้าง Twin ที่ Subscribe และรักษาสถานะจำลองให้สอดคล้องกับเครื่อง
- ส่งคำสั่งกลับไปยังเครื่องผ่านรูปแบบการสื่อสารที่เหมาะสม
- ทดสอบ Twin ทั้งกับข้อมูลสดและข้อมูลที่ Replay จากการบันทึก

ผลลัพธ์สำคัญของ Week 03 คือผู้เรียนได้เห็นว่า CLI, Inspector, Python Node, Recorder และ Digital Twin เป็นสมาชิกใน Graph เดียวกัน โดย Runtime กำหนดรูปแบบการสื่อสาร ส่วน Zenoh เป็น Transport ที่นำข้อมูลไปยังปลายทาง

## Week 04 — การเชื่อมต่อบอร์ดจริง

เอกสาร Week 04 เป็นร่างแผนการสอนสำหรับนำความรู้จากสัปดาห์ก่อนมาใช้กับบอร์ด ESP32-S3 จริง โดยบอร์ดทำหน้าที่เป็น Node ที่ขอบระบบ และเชื่อมเข้าสู่ Graph ผ่าน Host Bridge

กิจกรรมที่กำหนดไว้ในร่างประกอบด้วย

1. ค้นหาบอร์ดและตรวจสอบ Presence เพื่อยืนยันว่าอุปกรณ์เข้าร่วม Graph แล้ว
2. อ่าน Process Variable เช่น Battery, IMU หรือระดับเสียงผ่าน Topic
3. ส่งคำสั่งไปยัง Actuator เช่น LED หรือเสียง พร้อมตรวจสอบการตอบรับ
4. ปรับ Parameter ที่สามารถเก็บค่าไว้หลังปิด–เปิดเครื่อง
5. รับ Button Event แบบกด ปล่อย กดสั้น และกดยาว
6. บันทึกข้อมูลจริงจากบอร์ดและเล่นข้อมูลย้อนหลัง
7. เปรียบเทียบ Mini Digital Twin กับบอร์ดจริงแบบ Live และ Replay

ประเด็นเชิงสถาปัตยกรรมที่ได้เรียนรู้ ได้แก่

- Presence มีบทบาทคล้าย Watchdog หรือ Station-alive ในระบบ PLC
- Topic with Schema ทำหน้าที่แทน Fieldbus Tag ที่มีโครงสร้างชัดเจนกว่า
- Persisted Parameter เปรียบได้กับ Retained Setpoint หรือข้อมูลในหน่วยความจำถาวร
- Record/Replay เป็น Historian สำหรับข้อมูลหุ่นยนต์และอุปกรณ์ Edge
- การตรวจสอบ Capability จาก Topic ที่อุปกรณ์ประกาศ ช่วยให้โปรแกรมรองรับบอร์ดหลายรุ่นโดยไม่ผูกกับรายการฮาร์ดแวร์ตายตัว
- การประมวลผล Event บางส่วนบนอุปกรณ์ช่วยลดภาระและความซับซ้อนของ Host

## Week 05 — การบูรณาการและทบทวน

เนื่องจากยังไม่มีเอกสาร Week 05 ใน repository ส่วนนี้จึงใช้เป็นกรอบสำหรับรวบรวมและทบทวนความสัมพันธ์ของเนื้อหาที่เรียนมา ไม่ใช่บันทึกยืนยันกิจกรรมที่เกิดขึ้นจริง

แนวทางบูรณาการระบบทั้งชุดมีดังนี้

```text
Sensor / Actuator บนบอร์ด
            ↕
        Host Bridge
            ↕
     Middleware Graph
      ↙     ↓      ↘
Inspector Recorder Digital Twin
            ↓
    Analysis / Replay / Test
```

ระบบเริ่มจากอุปกรณ์จริงสร้างข้อมูล จากนั้น Bridge แปลงข้อมูลเข้าสู่ Message และ Schema ของ Middleware ข้อมูลถูก Publish ผ่าน Topic ให้ Inspector, Recorder และ Digital Twin นำไปใช้ ส่วนคำสั่งที่เป็นงานสั้นใช้ Service งานระยะยาวใช้ Action และค่าตั้งประจำ Node ใช้ Parameter

หัวข้อที่ควรทบทวนและสามารถใช้เป็นเกณฑ์ประเมินผลได้ ได้แก่

- ออกแบบขอบเขตและหน้าที่ของแต่ละ Node ได้เหมาะสม
- ตั้งชื่อ Topic และกำหนด Message Schema ที่สื่อความหมายและรองรับการขยายระบบ
- เลือก Topic, Service หรือ Action ให้ตรงกับลักษณะงาน
- ระบุ Frame และ Transform ของข้อมูลตำแหน่งได้อย่างถูกต้อง
- ใช้ Inspector, Record และ Replay เพื่อวิเคราะห์ปัญหา
- อธิบายเส้นทางข้อมูลระหว่างอุปกรณ์จริง Middleware และ Digital Twin ได้
- แยกงาน Hard Real-time ออกจากงานประสานระบบและงานแสดงผลได้
- คำนึงถึง Safety, Timeout, Validation และสถานะเมื่อ Node หรืออุปกรณ์ขาดการเชื่อมต่อ

## สรุปความรู้ที่ได้รับ

หลังผ่านเนื้อหาชุดนี้ ผู้เรียนควรสามารถ

1. อธิบายความแตกต่างระหว่างระบบ Automation แบบศูนย์กลางกับระบบ Robotics แบบกระจายได้
2. ออกแบบระบบโดยแบ่งหน้าที่เป็น Node และเชื่อมต่อกันผ่าน Topic
3. ใช้ Message และ Schema เป็นสัญญาข้อมูลระหว่างโปรแกรมและภาษา
4. เลือก Topic, Service, Action และ Parameter ให้เหมาะกับสถานการณ์
5. เข้าใจความสำคัญของ TF สำหรับข้อมูลตำแหน่งและการเคลื่อนที่
6. ตรวจสอบระบบด้วย Graph Inspector, Message Echo, Record และ Replay
7. สร้าง Mini Digital Twin ที่รับข้อมูลและโต้ตอบกับเครื่องจำลองหรืออุปกรณ์จริง
8. เชื่อมโยงแนวคิดใหม่กับประสบการณ์เดิมด้าน PLC, DCS, SCADA, Fieldbus และ Historian
9. มองเห็นข้อจำกัดด้านเวลา ความน่าเชื่อถือ และความปลอดภัยของระบบกระจาย

## บทสรุป

สาระสำคัญของรายวิชาไม่ได้อยู่ที่เครื่องมือเพียงตัวเดียว แต่อยู่ที่การเปลี่ยนวิธีออกแบบระบบ จากการรวม Logic ทั้งหมดไว้ใน Controller เดียว ไปสู่ระบบที่ประกอบด้วย Node หลายตัวซึ่งสื่อสารผ่านสัญญาข้อมูลที่ชัดเจน เมื่อรวมแนวคิดนี้เข้ากับการบันทึกข้อมูล การเล่นข้อมูลย้อนหลัง ระบบพิกัด และ Digital Twin จะทำให้สามารถพัฒนา ทดสอบ และตรวจสอบระบบอัตโนมัติได้ยืดหยุ่นและปลอดภัยยิ่งขึ้น
